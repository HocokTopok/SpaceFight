# Galactic Dominion — архитектура

До реализации прочитаны все 15 примеров `prompt/05.*.cpp` и полное ТЗ.
Используем C++23, CMake, SFML 3 (Graphics и Network). SFML TCP вместо
отдельного Asio уменьшает число зависимостей; сервер остаётся авторитетным.
Ядро не зависит от SFML и проверяется без графического окружения.

## Анализ предоставленных паттернов

| Материал | Паттерн / категория | Задача и классы | Решение |
|---|---|---|---|
| 05.01 | Builder / порождающий | PlanetBuilder, FrontierBuilder, CapitalBuilder: общий алгоритм и виртуальные шаги создания планеты | Да; аналог образца, с value/RAII владением |
| 05.02 | Factory Method / порождающий | ShipFactory, TypedShipFactory: создание четырёх типов кораблей через виртуальный метод | Да |
| 05.03 | Prototype / порождающий | Копирование шаблонов кораблей | Нет: небольшие value-описания проще |
| 05.04 | Adapter / структурный | Адаптер чужого интерфейса | Нет: несовместимых интерфейсов нет |
| 05.05 | Bridge / структурный | Независимые семейства рендереров | Нет: один рендерер |
| 05.06 | Composite / структурный | FleetComponent, Ship, FleetGroup: корабль → эскадрилья → армада | Да: рекурсивная агрегация боевых характеристик |
| 05.07 | Decorator / структурный | ShipUpgrade: оружие, броня, двигатель поверх FleetComponent | Да: комбинации исследований без подкласса на каждую |
| 05.08 | Memento / поведенческий | GameFacade::Memento: снимок перед ходом, отмена в одиночной игре | Да: value-снимок, без указателей на мир |
| 05.09 | Observer / поведенческий | EventBus, EventObserver, EventLog и визуальные эффекты | Да: независимые подписчики на события |
| 05.10 | State / поведенческий | Состояния планеты | Нет: владелец и оборона достаточно описывают правила |
| 05.11 | Strategy / поведенческий | AIStrategy и четыре конкретные стратегии | Да: сменные эвристики при общих правилах |
| 05.12 | Template Method / поведенческий | TurnProcessor::run, StandardTurn: фиксированный порядок и private virtual шаги | Да: NVI как в примере |
| 05.15 | Mixin / приём C++ | Операторы сравнения ресурсов | Нет: частичный порядок ресурсов не подходит; C++23 default comparison для value-типов |
| 05.17 | Singleton / порождающий | Глобальные сервисы | Нет: явное владение облегчает тесты и две независимые партии |
| 05.20 | Facade / структурный | GameFacade: приказы, разрешение хода, сохранение | Да: композиция подсистем вместо неуместного здесь variadic inheritance |

Дополнительно Command (OrderCommand, BuildCommand, MoveCommand, ResearchCommand,
ProduceCommand) связывает UI, AI и сетевой протокол с единым валидатором.
Abstract Factory не включаем: фракции симметричны, отличаются цветом и именем.

В блоках паттернов сохраняем скобки на новой строке, `public :`, виртуальные
деструкторы, `override`, `m_` для приватных полей и разделители `Pattern ...`.
Вместо ручного new/delete из примеров используем unique_ptr: идея владения та же,
но исключения и ранние выходы безопасны. Обычные пояснения находятся в документации.

## Подсистемы и поток данных

- `model`: ресурсы, планеты, корабли, технологии, карта; Builder, Factory, Composite, Decorator.
- `game`: Command, экономика, бои, исследования, Template Method, Observer, Facade, Memento.
- `ai`: четыре Strategy. Возвращает те же приказы, что игрок.
- `serialization`: ограниченный версионированный текстовый формат; проверка входных данных.
- `network`: неблокирующий TCP, кадры с ограничением размера, таймауты, два участника.
- `app`: SFML, главное меню, карта, панели, эффекты; только чтение модели и создание приказов.

UI/AI → очередь Command → проверка на копии → оба Ready → TurnProcessor →
движение → одновременный бой → экономика → производство → исследования → победа.
В LAN только host применяет команды и передаёт снимок. Клиент не назначает себе owner.
В одиночной игре AI планирует по исходному снимку без доступа к приказам человека.

## Правила

20 планет, связный зеркально симметричный граф; столицы в противоположных краях.
5 типов планет, 6 зданий, 4 корабля, 9 технологий в трёх цепочках.
Строительство/корабли оплачиваются при принятии приказа, завершаются после 1–3 ходов.
Флоты двигаются по одному ребру за приказ; длительность зависит от расстояния и скорости.
Встречные флоты проходят друг мимо друга, бой происходит у планеты. Прибытия одного хода
объединяются до боя. Урон обеих сторон вычисляется по состоянию до боя.
Защитные станции восстанавливают гарнизон; бомбардировщики усиливают атаку на гарнизон.
Отсутствие энергии снижает боеспособность на следующем ходу. Исследования действуют
на существующие корабли через Decorator. Radar и разведка раскрывают силы на расстоянии.
Захват столицы или всех колоний даёт победу; одновременная потеря столиц — ничья.

## Этапы и контрольные точки

1. 5%: анализ, архитектура, план (этот документ).
2. 25%: CMake, модель, генерация, обязательные структурные паттерны, headless проверки.
3. 50%: приказы, экономика, сражения, технологии, AI, save/load, undo.
4. 75%: полноценная игра с графикой, меню, исследованиями и визуальными слоями.
5. 90%: LAN, авторитетный сервер, интеграционные проверки.
6. 100%: сквозная проверка, визуальная полировка, инструкции, финальный checkpoint.

Каждый этап сохраняется отдельным Git-коммитом. PROGRESS.md хранит точку продолжения.
Проценты — оценка выполнения списка требований, не измерение затраченного времени.

## Итог реализации

Все шесть этапов выполнены. Для интеграции графического интерфейса транспорт LAN
был написан вместе с этапом 4; этап 5 закрепил его проверками авторитетности,
атомарности пакета, синхронизации событий и граничных размеров.
Реализации 10 заявленных паттернов реально используются игровыми подсистемами.
Итоговая структура и команды приведены в корневом README, доказательства проверок —
в VERIFICATION.md. Сохранения/протокол имеют собственный ограниченный текстовый
формат версии 1; сторонняя библиотека сериализации не требуется.
