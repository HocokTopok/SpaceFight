GALACTIC DOMINION

Техническое задание на разработку космической стратегии на C++23

1. Главная цель проекта

Необходимо разработать небольшую, но полноценную стратегическую компьютерную игру Galactic Dominion на C++23.

Игра представляет собой космическую стратегию, в которой два игрока соревнуются за контроль над галактикой, захватывают планеты, развивают экономику, строят сооружения, исследуют технологии, создают космические флоты и ведут войны.

В качестве концептуальных ориентиров можно использовать Galcon 2, Stellaris, Slipways и Mindustry.

Однако основная цель проекта заключается не только в создании игры, но и в демонстрации грамотного объектно-ориентированного проектирования программной системы на C++ с использованием паттернов проектирования.

Игра должна быть достаточно интересной, чтобы в неё действительно можно было играть, но при этом её реализация должна оставаться компактной, понятной и логично организованной.

Необходимо найти баланс между тремя направлениями:

1. Архитектура: осмысленное применение паттернов проектирования.
2. Игровой процесс: стратегическая глубина при относительно простых правилах.
3. Визуальная составляющая: красивая и атмосферная двумерная космическая стратегия.

Все три направления важны, однако архитектура C++ и демонстрация паттернов имеют особый приоритет, поскольку проект выполняется в рамках учебного задания.

2. Исходное учебное задание

Ниже приведено исходное задание, требования которого необходимо учитывать при проектировании всей системы.

Цитата задания:

Реализуйте систему программного каркаса для некоторой абстрактной стратегической компьютерной игры.

Используйте по крайней мере один порождающий паттерн проектирования, например, Builder, для контроля над созданием игровых объектов; один структурый паттерн проектирования, например, Composite, для организации взаимодействия игровых объектов и один поведенческий паттерн проектирования, например, Template Method, для управления поведением игровых объектов в системе.

Используйте любые другие паттерны проектирования при необходимости.

Поставьте себя на место архитектора или инженера данной программной системы.

Интерпретация задания

Нужно продемонстрировать не просто наличие классов с названиями паттернов, а реальное применение паттернов для решения архитектурных задач игры.

Обязательно использовать минимум три категории паттернов:

* Порождающие.
* Структурные.
* Поведенческие.

Желательно реализовать существенно больше трёх паттернов, если они естественно вписываются в проект.

При этом не следует искусственно усложнять код ради количества паттернов.

Главный критерий: каждый паттерн должен решать конкретную задачу и быть легко узнаваемым в исходном коде.

Эти файлы являются важной частью задания.

3. Разобраться в принципах их реализации.

5. Определить, какие паттерны наиболее естественно использовать в Galactic Dominion.
6. Составить архитектурный план с указанием назначения каждого паттерна.
7. Только после этого приступать к реализации.

Необходимо ориентироваться именно на предоставленные примеры, а не только на классические реализации паттернов из интернета.

* Организацию классов.
* Использование наследования.
* Виртуальные методы.
* Полиморфизм.
* Интерфейсы.

Не нужно дословно копировать примеры: необходимо сохранить их архитектурную идею и применить её к конкретной игровой механике.

4. Планирование архитектуры и паттернов

Перед написанием кода необходимо составить таблицу всех доступных паттернов из приложенных материалов.

Для каждого паттерна определить:

* Название.
* Категорию.
* Возможное применение в игре.
* Какие классы будут участвовать.
* Какую проблему решает.
* Насколько естественно вписывается в архитектуру.
* Стоит ли включать его в итоговую реализацию.

Желательно использовать максимально возможное количество действительно полезных паттернов, но без создания избыточных абстракций.

Предварительно предлагается следующая архитектура.

4.1. Порождающие паттерны

Builder — создание планет

Использовать для пошагового конструирования планет с различными характеристиками.

Например, планета может иметь:

* Название.
* Тип поверхности.
* Размер.
* Запасы ресурсов.
* Производительность.
* Количество строительных слотов.
* Начальные сооружения.
* Оборонительные характеристики.

Builder должен позволять создавать разные конфигурации планет через единый понятный интерфейс.

Factory Method — создание кораблей

Использовать для создания разных типов космических кораблей.

Например:

* Fighter.
* Frigate.
* Cruiser.
* Bomber.

Каждый тип корабля имеет собственные характеристики и особенности.

Abstract Factory — создание игровых фракций

Если это не приведёт к существенному усложнению, можно использовать для создания связанных наборов объектов разных фракций.

Например, фракции могут отличаться кораблями, визуальным оформлением и стартовыми бонусами.

Необходимо оценить, оправдан ли этот паттерн для небольшой игры.

4.2. Структурные паттерны

Composite — организация флотов

Один из обязательных и наиболее важных паттернов.

Предлагается организовать иерархию:

* Отдельный корабль.
* Флот из нескольких кораблей.
* Группа флотов.

При этом отдельный корабль и составная группа должны предоставлять общий интерфейс для выполнения определённых операций.

Например:

* Получение общей боевой мощи.
* Получение характеристик защиты.
* Подсчёт количества кораблей.
* Выполнение боевых действий.

Это позволит наглядно продемонстрировать рекурсивную композицию игровых объектов.

Decorator — улучшения кораблей

Можно использовать для добавления модификаций:

* Улучшенное вооружение.
* Усиленная броня.
* Дополнительные двигатели.

Модификации должны изменять характеристики кораблей без необходимости создавать отдельный класс для каждой комбинации улучшений.

Однако следует оценить, не окажется ли обычная система характеристик проще и понятнее.

Facade — управление игровой системой

Можно создать единый интерфейс для основных игровых действий:

* Начало партии.
* Выполнение хода.
* Строительство.
* Перемещение флота.
* Обработка сражений.
* Проверка победы.

Facade должен скрывать взаимодействие отдельных подсистем, не превращаясь в монолитный класс со всей игровой логикой.

4.3. Поведенческие паттерны

Template Method — обработка игрового хода

Один из обязательных паттернов.

Использовать для определения общего алгоритма игрового хода.

Например:

1. Получение приказов.
2. Проверка допустимости действий.
3. Перемещение флотов.
4. Обработка сражений.
5. Производство ресурсов.
6. Выполнение строительства.
7. Обновление исследований.
8. Проверка условий победы.

Общий порядок выполнения действий должен быть определён базовым классом.

Отдельные этапы могут переопределяться в производных классах.

Необходимо сделать так, чтобы Template Method действительно использовал наследование и виртуальные методы, а не представлял собой обычную функцию, вызывающую несколько других функций.

Strategy — искусственный интеллект

Использовать для реализации разных стратегий компьютерного противника:

* AggressiveStrategy.
* EconomicStrategy.
* DefensiveStrategy.
* ScientificStrategy.

Каждая стратегия должна выбирать действия на основании текущего состояния игры.

Общий интерфейс позволит переключать поведение ИИ без изменения основной игровой логики.

Command — игровые приказы

Использовать для представления действий игрока отдельными объектами.

Например:

* BuildCommand.
* MoveFleetCommand.
* ResearchCommand.
* UpgradeCommand.

Это особенно полезно для пошаговой игры и сетевого режима.

Игрок формирует набор приказов, которые затем проверяются и выполняются игровой системой.

Observer — игровые события

Использовать для уведомления различных подсистем о событиях.

Например:

* Планета захвачена.
* Строительство завершено.
* Флот уничтожен.
* Технология исследована.
* Игрок победил.

На события могут реагировать интерфейс, журнал событий и другие игровые компоненты.

State — состояние планеты

При необходимости можно выделить состояния:

* Neutral.
* Colonized.
* UnderAttack.
* Occupied.

Разные состояния могут влиять на доступные действия и поведение планеты.

Использовать State только в том случае, если он действительно упрощает управление состояниями.

Memento — сохранение игрового состояния

Можно реализовать сохранение и восстановление состояния партии.

Например:

* Сохранение состояния перед ходом.
* Возможность отмены последнего хода в одиночном режиме.
* Восстановление сохранённой партии.

При этом важно не усложнять проект полноценной системой сериализации, если достаточно небольших снимков игрового состояния.

5. Особые требования к реализации паттернов

Это один из наиболее важных разделов задания.

Все паттерны должны быть максимально наглядно представлены в исходном коде.

Необходимо соблюдать следующие правила.

5.1. Выделение реализаций паттернов

Части кода, в которых непосредственно реализуются паттерны проектирования, необходимо выделять разделителями:

///////////////////////////////////////////////////////////////////////////////
// Pattern Builder
///////////////////////////////////////////////////////////////////////////////
class PlanetBuilder
{
    // ...
};
///////////////////////////////////////////////////////////////////////////////

Аналогично:

///////////////////////////////////////////////////////////////////////////////
// Pattern Composite
///////////////////////////////////////////////////////////////////////////////
///////////////////////////////////////////////////////////////////////////////
// Pattern Template Method
///////////////////////////////////////////////////////////////////////////////
///////////////////////////////////////////////////////////////////////////////
// Pattern Strategy
///////////////////////////////////////////////////////////////////////////////

Разделители должны визуально отделять реализацию одного паттерна от остальных компонентов.

Если паттерн занимает несколько классов, желательно сгруппировать их в одном логическом блоке.

Если реализация распределена по нескольким файлам, следует сохранить понятную структуру и выделить основные части паттерна.

5.2. Стиль написания C++

Для выделенных блоков с паттернами особенно важно ориентироваться на стиль C++ из приложенных файлов.

Следует учитывать:

* Форматирование классов.
* Расположение спецификаторов доступа.
* Расстановку фигурных скобок.
* Форматирование конструкторов.
* Форматирование виртуальных методов.
* Использование auto.
* Пробелы между элементами синтаксиса.
* Организацию наследования.
* Форматирование шаблонов.
* Стиль объявления полей.

Остальной код можно писать в обычном аккуратном стиле C++23.

5.3. Комментарии

Обычные комментарии в коде не нужны.

Не следует добавлять комментарии к каждой функции, переменной или условию.

Код должен быть понятен благодаря:

* Названиям классов.
* Названиям методов.
* Логичной организации.
* Небольшим функциям.
* Чётким интерфейсам.

Исключение — специальные заголовки паттернов и разделители.

Например:

///////////////////////////////////////////////////////////////////////////////
// Pattern Observer
///////////////////////////////////////////////////////////////////////////////

Также допускаются краткие обозначения логических разделов, если это необходимо для читаемости.

5.4. Простота реализации

Нужно избегать ситуаций, когда ради одного паттерна создаётся десяток классов, которые почти ничего не делают.

Каждый паттерн должен:

* Иметь реальную задачу.
* Использоваться в игровом процессе.
* Быть понятным при чтении кода.
* Не требовать чрезмерного количества вспомогательных классов.

Предпочтение следует отдавать небольшим, но показательным реализациям.

6. Игровая механика

6.1. Основной игровой цикл

Galactic Dominion — пошаговая космическая стратегия для двух игроков.

Карта содержит примерно 15–25 планет.

Каждый игрок начинает с одной развитой планеты и небольшого флота.

Остальные планеты нейтральны и доступны для колонизации или захвата.

Игроки должны:

* Развивать собственные планеты.
* Добывать ресурсы.
* Строить сооружения.
* Производить корабли.
* Исследовать технологии.
* Захватывать территории.
* Защищать собственную империю.

Победа достигается захватом столицы противника или уничтожением всех его колоний.

6.2. Одновременные ходы

Оба игрока независимо формируют приказы.

После подтверждения обоих игроков система одновременно обрабатывает их действия.

Это позволяет реализовать интересную стратегическую механику, в которой игрок должен предугадывать действия противника.

В режиме против ИИ компьютер формирует свои приказы автоматически.

7. Ресурсы и экономика

Использовать три основных ресурса.

Металл

Применяется для:

* Строительства кораблей.
* Возведения сооружений.
* Улучшения планетарной обороны.

Энергия

Применяется для:

* Работы сооружений.
* Содержания флотов.
* Строительства специальных объектов.

Наука

Используется для:

* Исследования технологий.
* Улучшения характеристик кораблей.
* Развития экономики.

Каждая планета производит ресурсы в зависимости от своего типа, характеристик и построенных сооружений.

Ресурсы поступают в общий запас игрока.

Не требуется реализовывать сложную торговую систему или полноценную экономическую симуляцию.

Однако экономика должна создавать реальные стратегические решения.

Например, игрок может вложить ресурсы в промышленность, исследования или производство флота.

8. Типы планет

Планеты должны различаться не только характеристиками, но и внешним видом.

Предусмотреть несколько типов.

Землеподобная планета

Внешний вид:

* Океаны.
* Континенты.
* Облака.
* Атмосфера.

Особенности:

* Сбалансированное производство ресурсов.
* Подходит для универсального развития.

Пустынная планета

Внешний вид:

* Песчаные поверхности.
* Кратеры.
* Горные массивы.

Особенности:

* Высокая добыча металла.

Ледяная планета

Внешний вид:

* Ледяные равнины.
* Трещины.
* Холодная голубая атмосфера.

Особенности:

* Повышенный научный потенциал.

Вулканическая планета

Внешний вид:

* Тёмная поверхность.
* Лавовые трещины.
* Красно-оранжевое свечение.

Особенности:

* Высокое производство энергии.

Газовый гигант

Внешний вид:

* Атмосферные полосы.
* Облачные вихри.
* Кольца.

Особенности:

* Высокая добыча энергии.
* Возможность строительства орбитальных сооружений.

Каждая планета имеет:

* Название.
* Тип.
* Размер.
* Владельца.
* Производство ресурсов.
* Строительные слоты.
* Сооружения.
* Защитные характеристики.
* Космические корабли на орбите.

9. Сооружения

Каждая планета имеет ограниченное количество строительных слотов.

Предлагаемые здания:

Здание	Назначение
Mine	Производство металла
PowerPlant	Производство энергии
Laboratory	Производство науки
Shipyard	Производство кораблей
DefenseStation	Защита планеты
Radar	Разведка

Сооружения должны непосредственно влиять на игровой процесс.

При этом желательно визуально отображать развитие планет.

Например:

* После строительства верфи появляется орбитальная станция.
* После строительства обороны появляются защитные спутники.
* После строительства энергетических сооружений на планете возникают светящиеся элементы.
* Развитые планеты выглядят более технологичными.

Для этого можно использовать небольшие двумерные спрайты и анимации.

Не нужно моделировать полноценные трёхмерные города.

10. Космические корабли и флоты

Реализовать четыре основных типа кораблей.

Корабль	Особенности
Fighter	Быстрый и дешёвый
Frigate	Универсальный
Cruiser	Мощный и дорогой
Bomber	Эффективен против планетарной обороны

Корабли объединяются во флоты.

Игрок может отправлять флоты между планетами, соединёнными гиперпространственными маршрутами.

Разные типы кораблей должны иметь различные характеристики:

* Атака.
* Защита.
* Скорость.
* Стоимость.

Боевая система должна быть математической и относительно простой.

Не требуется моделировать отдельные снаряды, физику столкновений или сложное поведение каждого корабля.

Однако сражения должны сопровождаться визуальными эффектами.

⸻

11. Технологии

Предусмотреть небольшое дерево исследований из трёх веток.

Экономические технологии

* Повышение добычи ресурсов.
* Ускорение строительства.
* Снижение стоимости производства.

Военные технологии

* Улучшение вооружения.
* Усиление защиты.
* Открытие тяжёлых кораблей.

Космические технологии

* Ускорение флотов.
* Улучшение разведки.
* Повышение мобильности.

Достаточно 9–12 технологий.

Игрок должен выбирать направление развития.

Необходимо обеспечить несколько жизнеспособных стратегий, чтобы игра не сводилась к единственному оптимальному порядку действий.

⸻

12. Искусственный интеллект

Предусмотреть режим игры против компьютера.

ИИ должен уметь:

* Оценивать доступные планеты.
* Захватывать нейтральные территории.
* Строить сооружения.
* Производить корабли.
* Атаковать противника.
* Защищать собственные территории.
* Исследовать технологии.

Не нужно использовать машинное обучение.

Достаточно простых эвристических алгоритмов.

Желательно реализовать несколько стратегий поведения, чтобы продемонстрировать паттерн Strategy.

Например:

* Агрессивный ИИ.
* Экономический ИИ.
* Оборонительный ИИ.

⸻

13. Мультиплеер по локальной сети

Предусмотреть возможность игры двух человек по локальной сети.

Один игрок создаёт сервер, второй подключается по IP.

Использовать простую клиент-серверную архитектуру.

Сервер отвечает за:

* Получение приказов.
* Проверку действий.
* Выполнение игрового хода.
* Обновление состояния.
* Определение победителя.

Поскольку игра пошаговая, нет необходимости реализовывать высокочастотную синхронизацию.

Достаточно передавать приказы игроков и обновлённое игровое состояние.

Сетевой режим должен использовать ту же игровую логику, что и одиночный.

Если сетевой режим значительно увеличивает сложность первоначальной реализации, его можно выделить в отдельный этап.

⸻

14. Визуальная составляющая

Визуальное оформление — один из главных приоритетов проекта.

Несмотря на относительно простую игровую логику, Galactic Dominion должна выглядеть как небольшая современная космическая стратегия.

Необходимо избегать примитивного оформления, в котором планеты представляют собой обычные одноцветные круги.

14.1. Общий стиль

Предпочтительный стиль:

* Тёмный космический фон.
* Красивые текстуры планет.
* Мягкое освещение.
* Небольшие туманности.
* Звёздные поля.
* Футуристический интерфейс.
* Аккуратные анимации.
* Плавные визуальные переходы.

Визуально игра должна напоминать небольшую атмосферную indie-стратегию.

14.2. Планеты

Планеты должны иметь:

* Различные текстуры.
* Атмосферную подсветку.
* Освещённую и затемнённую стороны.
* Облака или другие детали поверхности.
* Кольца у некоторых типов.
* Спутники.
* Орбитальные сооружения.
* Плавное вращение или его визуальную имитацию.

Можно использовать заранее подготовленные двумерные текстуры.

Не требуется настоящий 3D-рендеринг.

Вместо сложной процедурной генерации предпочтительнее качественные готовые изображения, спрайты и простые эффекты.

14.3. Живой космос

Карта должна создавать ощущение живого мира.

Желательно добавить:

* Медленное движение звёзд.
* Мерцание отдельных источников света.
* Движущиеся космические флоты.
* Орбитальные станции.
* Небольшие транспортные корабли.
* Визуальные эффекты энергетических сооружений.
* Периодические вспышки.
* Светящиеся маршруты.
* Анимации космических сражений.

При этом декоративные эффекты не должны требовать сложной игровой логики.

14.4. Визуальное развитие планет

Особенно важно, чтобы строительство сооружений отражалось на внешнем виде планеты.

Например, изначально нейтральная планета выглядит практически необитаемой.

После колонизации появляются:

* Орбитальные спутники.
* Небольшие светящиеся поселения.
* Космические станции.
* Защитные системы.
* Промышленные объекты.

По мере развития планета должна выглядеть более населённой и технологичной.

Для реализации достаточно нескольких визуальных слоёв и спрайтов, которые включаются в зависимости от построенных сооружений.

Не требуется создавать сложную систему процедурного изменения поверхности.

⸻

15. Пользовательский интерфейс

Интерфейс должен быть современным, понятным и визуально аккуратным.

Верхняя панель

Отображает:

* Металл.

* Науку.

Центральная область

* Планеты.

* Флоты.
* Эффекты.
* Подсветка выбранных объектов.

Правая панель

Информация о выбранной планете:

* Название.
* Тип.
* Владелец.
* Ресурсы.
* Сооружения.
* Корабли.
* Доступные действия.

Дополнительные элементы

* Окно исследований.
* Панель строительства.

* Экран победы или поражения.

При этом интерфейс не должен требовать создания собственной сложной UI-библиотеки.

16. Технические требования

Основной язык — C++23.

Предпочтительный стек:

* C++23.
* SFML 3.
* CMake.
* Стандартная библиотека C++.
* Asio или Boost.Asio для сетевого режима.

Поддерживаемые платформы:

* macOS, включая Apple Silicon.
* Linux.

Не использовать тяжёлые игровые движки.

Желательно минимизировать внешние зависимости.

Проект должен собираться через CMake.

Организация исходного кода

Необходимо разделить проект на логические компоненты:

* Core — основные игровые сущности.
* Galaxy — планеты и галактическая карта.
* Economy — ресурсы и сооружения.
* Fleet — корабли и флоты.
* Combat — боевая система.
* Research — технологии.
* AI — компьютерный противник.
* Graphics — визуализация.
* UI — интерфейс.
* Network — сетевой режим.

Это пример логического разделения, а не требование создавать отдельный файл для каждого компонента.

Не нужно искусственно увеличивать количество файлов и классов.

Если несколько небольших компонентов удобно разместить в одном файле, это допустимо.

Особое внимание уделить отделению игровой логики от визуализации.

Графическая подсистема должна отображать состояние игры, а не определять игровые правила.

⸻

17. Ограничение сложности

Необходимо помнить, что проект является учебным.

Главная задача — продемонстрировать качественную архитектуру и паттерны проектирования, а не создать огромную коммерческую стратегию.

Не следует реализовывать:

* Сложную физику.
* Полноценный 3D.
* Большое количество ресурсов.
* Сложную торговлю.
* Десятки типов кораблей.
* Огромные технологические деревья.
* Сложную симуляцию населения.
* Многоуровневую дипломатическую систему.
* Ненужные архитектурные абстракции.

При выборе между двумя решениями предпочтение следует отдавать тому, которое:

1. Проще понять.
2. Требует меньше кода.
3. Лучше демонстрирует паттерны.
4. Легче расширяется.
5. Не ухудшает игровой процесс.

При этом не следует чрезмерно упрощать визуальную составляющую.

Красивые текстуры, спрайты и анимации могут создавать ощущение полноценной игры без существенного усложнения C++.

⸻

Не начинай сразу писать весь код игры.

Сначала необходимо спроектировать систему.

Шаг 1. Анализ приложенных материалов

Изучи все файлы с примерами паттернов.

Определи:

* Какие паттерны доступны.
* Какие реализации используются.
* Какие особенности C++ демонстрируются.
* Какой стиль написания кода необходимо соблюдать.

Шаг 2. Архитектурное проектирование

Предложи архитектуру Galactic Dominion.

Укажи:

* Основные классы.
* Взаимодействия между ними.
* Ответственность каждого компонента.
* Используемые паттерны.
* Причины выбора паттернов.

Отдельно составь таблицу соответствия:

Паттерн → игровая задача → классы → принцип работы.

Шаг 3. Планирование реализации

Раздели разработку на небольшие этапы.

Каждый этап должен приводить к конкретному работоспособному результату.

Приоритет:

1. Базовая игровая логика.
2. Обязательные паттерны.
3. Экономика и развитие.
4. Графический интерфейс.
5. Дополнительные паттерны.
6. Искусственный интеллект.
7. Сетевой режим.
8. Полировка визуального оформления.

При этом качественные базовые текстуры и визуальный стиль должны присутствовать уже в ранней играбельной версии.

Шаг 4. Реализация

После согласования архитектуры приступай к написанию кода.

Соблюдай:

* C++23.
* Простой и понятный код.
* Стиль приложенных примеров для паттернов.
* Выделение паттернов разделителями.
* Минимум комментариев.
* Разделение ответственности.
* Корректное управление ресурсами.

Шаг 5. Проверка

После реализации необходимо проверить:

* Компиляцию.
* Запуск.
* Работу основных механик.
* Корректность игровой логики.
* Отсутствие очевидных ошибок.
* Реальное использование каждого заявленного паттерна.
* Соответствие архитектуры исходному заданию.

Если паттерн присутствует в коде, но фактически не используется, это необходимо исправить либо исключить его из итогового списка.

19. Ожидаемый результат

В результате должен получиться полноценный проект Galactic Dominion на C++23.

Игра должна:

* Запускаться локально на macOS и Linux.
* Иметь красивую двумерную галактическую карту.
* Содержать разнообразные планеты.
* Позволять строить сооружения и развивать экономику.
* Поддерживать производство кораблей и управление флотами.
* Иметь технологическое развитие.
* Предоставлять возможность сражаться против компьютера.
* Предусматривать PvP по локальной сети.
* Демонстрировать несколько жизнеспособных стратегий развития.

Но главное — проект должен наглядно демонстрировать применение паттернов проектирования на C++.

Обязательные паттерны:

* Минимум один порождающий.
* Минимум один структурный.
* Минимум один поведенческий.

Дополнительные паттерны следует использовать там, где они действительно улучшают архитектуру.

Все основные реализации паттернов должны быть явно выделены в коде разделителями:

///////////////////////////////////////////////////////////////////////////////
// Pattern <Name>
///////////////////////////////////////////////////////////////////////////////

Для этих блоков необходимо соблюдать стиль приложенных примеров.

Остальной код можно писать в обычном аккуратном стиле C++23, без лишних комментариев.

Главные принципы разработки

1. Паттерны должны быть частью работающей игры, а не отдельными демонстрационными примерами.

2. Код должен быть компактным, понятным и архитектурно грамотным.

3. Визуальная составляющая должна создавать ощущение красивого и живого космического мира.

4. Стратегическая глубина должна достигаться взаимодействием небольшого количества простых механик.

5. Необходимо ориентироваться на приложенные материалы по паттернам и использовать их стиль реализации.

6. Перед написанием кода необходимо тщательно спланировать архитектуру и распределение паттернов.

7. Не следует реализовывать весь проект одним большим блоком. Разработка должна быть последовательной и проверяемой.

Итоговая цель — создать небольшую, красивую и интересную космическую стратегию, которая одновременно является качественным примером архитектуры программной системы на современном C++.
